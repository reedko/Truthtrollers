# CFX → EvidenceRun Initial Query and Retrieval Specification

**Date:** 2026-07-31
**Status:** Proposed first retrieval experiment
**Scope:** Query planning, provider routing, candidate retrieval, deduplication, and review artifacts only
**Non-goal:** Do not yet build final bearing, stance, scoring, or portfolio selection

## 1. Objective

For each accepted CFX proposition, produce a small, diverse set of search queries, retrieve a bounded candidate pool, and generate a review report showing what the queries actually found.

The first experiment should answer:

> Can the current CFX evidence-search handoff reliably retrieve sources that materially bear on each proposition?

Do not optimize for a polished final EvidenceRun yet. First expose query quality, provider behavior, candidate relevance, and failure modes.

## 2. Governing CFX input

Each proposition enters EvidenceRun unchanged:

```ts
type CfxEvidenceInput = {
  propositionId: string;
  substantiveAssertion: string;
  assertionSource: string;
  articleStance: "adopts" | "challenges" | "reports";
  groundingUnitIds: string[];
  groundingText: string;

  literalIdentifiers: {
    people: string[];
    organizations: string[];
    laws: string[];
    studyTitles: string[];
    journals: string[];
    years: string[];
    dateRanges: string[];
    acronyms: string[];
    doi: string[];
    pmid: string[];
    urls: string[];
    citationNumbers: string[];
  };

  lookupHints: {
    populations: string[];
    exposures: string[];
    interventions: string[];
    outcomes: string[];
    geography: string[];
    documentTypes: string[];
    topics: string[];
  };

  deterministicQueries: {
    literalQuery: string | null;
    sourceQualifiedQuery: string | null;
    studyLookupQueries: string[];
  };
};
```

The canonical `substantiveAssertion` is immutable.

## 3. Initial query budget

Create **five initial query lanes per proposition**.

Five means five meaningfully different retrieval attempts, not five cosmetic rewrites.

### Q1 — Canonical assertion

Purpose: find exact or near-exact discussion of the proposition.

Build from the substantive assertion with light mechanical cleanup only.

Example:

```text
CDC manipulated data linking MMR vaccine to autism
```

Do not require quotation marks around the entire assertion by default. Preserve a quoted form as an optional variant for diagnostics.

### Q2 — Predicate and entities

Purpose: search the core relationship using literal entities and concepts.

Build from:

- named people or organizations;
- intervention or exposure;
- outcome;
- causal, comparative, safety, legal, or historical predicate.

Example:

```text
CDC MMR autism data manipulation
```

### Q3 — Source or named-work lookup

Purpose: locate the specific person, institution, law, report, study, advertisement, or document associated with the assertion.

Use only when a useful source identity exists.

Examples:

```text
William Thompson CDC MMR autism study
National Childhood Vaccine Injury Act manufacturer liability
```

If the source label is generic, such as `historical context provided in the article`, do not include it.

### Q4 — Independent evidence

Purpose: find primary or high-quality evidence addressing the proposition without depending on the article's source wording.

Use proposition entities plus the evidence relationship.

Examples:

```text
ethylmercury vaccine neurotoxicity evidence
childhood vaccine schedule chronic disease cohort study
```

Do not add verdict words such as `true`, `false`, or `debunked`.

### Q5 — Counterevidence or material qualification

Purpose: deliberately search for evidence that may contradict, limit, or qualify the proposition.

The query should target the alternative evidentiary possibility, not simply append `refute`.

Examples:

```text
ethylmercury vaccine safety pharmacokinetics
MMR autism reanalysis CDC Thompson critique
vaccine manufacturer liability exceptions 1986 Act
```

This lane may be generated by a small query-planning model call because mechanical negation is unsafe. It must not alter the canonical proposition.

## 4. PubMed applicability and query lane

A proposition is PubMed-applicable when its assertion or literal hints concern a biomedical relationship such as:

- population, intervention or exposure, and health outcome;
- drug, vaccine, ingredient, toxicity, adverse event, disease, diagnosis, mortality, or hospitalization;
- epidemiology, clinical safety, pharmacokinetics, immunology, toxicology, or public-health outcomes;
- an explicitly referenced biomedical study.

Use a deterministic applicability gate from literal fields and a small controlled vocabulary. Record the reasons the gate fired.

When PubMed applies:

- Q4 should normally be a PubMed query;
- Q5 may also be PubMed when the proposition is best tested in biomedical literature;
- do not exceed **two PubMed queries** in the initial five-query budget.

A PubMed query should be built from literal PICO-style components where available:

```text
(population) AND (intervention OR exposure) AND (outcome)
```

Example:

```text
infants AND vaccination AND (hospitalization OR mortality)
```

Add literal date ranges, named authors, or study titles only when present.

Do not invent MeSH terms or bibliographic identities. A later PubMed adapter may map literal terms to MeSH.

## 5. Query planning implementation

Use a hybrid approach:

### Deterministic code

Responsible for:

- normalization;
- deduplication;
- identifier extraction;
- source-label suppression;
- provider applicability;
- exact identifiers such as DOI, PMID, title, author, law, and date;
- query length limits;
- duplicate-term removal;
- query-lane accounting.

### One small query-planning model call

Responsible only for:

- Q2 predicate/entity wording;
- Q4 independent-evidence wording;
- Q5 counterevidence or qualification wording;
- choosing which of the five lanes should route to PubMed.

Input:

- immutable substantive assertion;
- assertion source;
- article stance;
- literal identifiers;
- lookup hints;
- grounding text.

Output:

```ts
type QueryPlan = {
  propositionId: string;
  queries: Array<{
    queryId: "Q1" | "Q2" | "Q3" | "Q4" | "Q5";
    query: string;
    lane:
      | "canonical"
      | "predicate_entities"
      | "source_identity"
      | "independent_evidence"
      | "counterevidence_qualification";
    provider: "web" | "pubmed";
    rationale: string;
  }>;
};
```

The model may not rewrite the assertion or return a replacement target.

If a deterministic exact-identity query already occupies a lane, preserve it rather than asking the model to regenerate it.

## 6. Retrieval budget

For the first experiment:

- 5 queries per proposition;
- top 5 normalized candidates per query;
- maximum 25 raw candidates per proposition;
- deduplicate by DOI, PMID, canonical URL, normalized title, and provider identifier;
- retain query-to-candidate provenance;
- do not fetch full text yet unless already available through the provider response.

For 12 propositions:

- maximum 60 query executions;
- maximum 300 raw candidate slots before deduplication.

This is large enough to reveal retrieval quality and still small enough to inspect.

## 7. Candidate normalization

Persist at minimum:

```ts
type EvidenceCandidate = {
  candidateId: string;
  propositionId: string;
  queryId: string;
  provider: string;
  providerRecordId: string | null;
  title: string;
  authors: string[];
  publication: string | null;
  publicationDate: string | null;
  doi: string | null;
  pmid: string | null;
  url: string | null;
  abstractOrSnippet: string | null;
  sourceType: string | null;
  retrievalRank: number;
  rawArtifactPath: string;
};
```

No semantic bearing judgment is required in this milestone.

## 8. Deterministic deduplication

Deduplicate in this order:

1. DOI;
2. PMID;
3. provider-native identifier;
4. canonical URL;
5. normalized title plus year;
6. normalized title alone only when highly similar.

Never discard query provenance. A deduplicated candidate should retain every query and provider path that found it.

## 9. First review report

Generate a self-contained `report.html` and JSON artifacts.

For each proposition, show:

- canonical assertion;
- assertion source;
- article stance;
- grounding units and text;
- literal identifiers and lookup hints;
- the five queries;
- provider selected for each query;
- all returned candidates grouped by query;
- deduplicated candidate list;
- candidate title, authors, date, publication, DOI, PMID, URL, and snippet or abstract;
- duplicate merges;
- provider failures;
- request count, tokens, latency, and estimated cost.

Add manual review fields:

- bears directly;
- possibly bears;
- topic only;
- irrelevant;
- duplicate;
- inaccessible;
- not reviewed.

Do not automatically declare evidence stance or final source quality.

## 11. Acceptance criteria

The milestone passes when:

- every proposition has exactly five distinct query lanes or an explicit typed reason for a missing lane;
- no query changes the canonical assertion;
- generic source labels are not inserted into queries;
- PubMed routing is explainable and bounded;
- DOI, PMID, title, author, law, and date identities are preserved exactly;
- every candidate retains query and provider provenance;
- deduplication does not erase discovery paths;
- the report makes query quality and retrieval quality inspectable;
- provider failures do not erase successful sibling queries;
- no final bearing, evidence stance, score, or claim rewrite is introduced.

## 12. Repository mining targets

Before writing new code, search the repository for tested utilities in:

- TM4 / TM5 EvidenceRun;
- CF1–CF7;
- legacy production evidence retrieval;
- provider adapters;
- PubMed clients;
- Crossref, Semantic Scholar, Google or Bing adapters;
- DOI / PMID / URL normalization;
- query planning and lane compilation;
- candidate normalization;
- deduplication;
- title similarity;
- report generation;
- token and cost accounting;
- retry and provider-failure isolation.

Prefer adapters around tested code. Do not import old orchestration, semantic selectors, scoring, bearing logic, or claim mutation merely to reuse one utility.

## 13. Build sequence

1. Repository audit and exact reuse map.
2. Freeze the CFX evidence input contract.
3. Implement five-lane query planning.
4. Add PubMed applicability and provider routing.
5. Execute retrieval only, with bounded candidate counts.
6. Normalize and deduplicate.
7. Generate the review report.
8. Inspect results before building bearing or stance adjudication.

Stop after the retrieval report. The next architecture decision must be based on what the queries actually find.
